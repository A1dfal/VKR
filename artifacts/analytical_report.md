
# Аналитический отчёт

**Тема ВКР:** «Разработка системы анализа качества процессов разработки проектов с открытым исходным кодом».

**Дата редакции:** 22 октября 2026 года.

## Постановка исследовательской задачи

При выборе открытого компонента разработчику или специалисту по информационной безопасности нужно оценить его состояние и условия сопровождения. Для решения требуются сведения о зависимостях, проверках кода, принятии изменений и подготовке выпусков. NIST SSDF, SLSA и OWASP SCVS связывают эти вопросы с практиками безопасной разработки, происхождением программного обеспечения и условиями его применения. [1](#source-N1), [2](#source-N2), [3](#source-N3)

Потребитель компонента принимает решение с учётом своего приложения: используемой версии, выполняемых функций, доступных прав и последствий возможной проблемы. Ему требуется понять, какие обстоятельства допускают внедрение, какие требуют исправления или дополнительной проверки и к каким условиям относится полученный вывод. Поэтому результат анализа должен связывать наблюдаемые сведения с конкретным действием.

Зависимости расширяют круг участников, которым доверяет потребитель. В исследовании Zimmermann и соавторов средний пакет npm транзитивно зависел от кода примерно 40 сопровождающих; данные охватывали историю до апреля 2018 года. Ohm и соавторы собрали 174 вредоносных пакета npm, PyPI и RubyGems за ноябрь 2015 — ноябрь 2019 года. Эти результаты показывают значение связей между компонентами, сопровождающими и выпусками. [4](#source-RS1), [5](#source-RS2)

Инцидент XZ Utils с выпусками 5.6.0 и 5.6.1 показывает важность проверки конкретного распространяемого артефакта и его связи с репозиторием. Поэтому рекомендация об использовании проекта должна относиться к выбранной версии и опираться на проверяемые сведения о ней. [6](#source-XZ1)

Практическая трудность состоит в распределении этих сведений между разными источниками. Анализатор зависимостей сообщает о компонентах и известных проблемах, проверка репозитория — о наблюдаемых практиках, история изменений — об участии разработчиков. Потребителю приходится самостоятельно устанавливать, относятся ли результаты к одному объекту, насколько они актуальны и что означают для его условий использования. Эта работа определяет предмет сравнительного анализа.

Цель аналитического этапа — сопоставить возможности существующих средств и определить, какие сведения и способы их интерпретации нужны для рекомендации об использовании открытого проекта с учётом рисков информационной безопасности и внедрения бэкдоров.

## Выбор средств и методика сравнения

В обзор включены коммерческие платформы, встроенные средства GitHub и открытые инструменты. Модули с разным назначением рассмотрены отдельно: CodeScoring SCA с OSA и TQI, GitHub Dependabot и CodeQL.

Состав выборки отражает последовательность работы с внешним компонентом: установить зависимости, получить сведения об их проблемах, изучить собственный код проекта, рассмотреть контроль изменений и историю участия, затем определить необходимые действия. Коммерческие платформы показывают возможности централизованного анализа и политик; средства GitHub — проверки в среде репозитория; открытые инструменты — способы получения процессных сведений и учёта состава приложения.

| Решение | Назначение |
|---|---|
| CodeScoring SCA + OSA | Выявить проблемы сторонних компонентов и применить политики при их использовании. |
| CodeScoring TQI | Изучить распределение вкладов, динамику изменений и метрики кода. |
| Snyk Open Source | Находить и исправлять известные проблемы открытых библиотек. |
| Sonatype Lifecycle | Контролировать риски компонентов на этапах жизненного цикла приложения. |
| Socket | Выявлять подозрительные свойства зависимостей и изменения при их публикации. |
| GitHub Dependabot | Сообщать об известных проблемах зависимостей и помогать обновлять их. |
| GitHub CodeQL | Находить потенциальные уязвимости и ошибки в коде проекта. |
| OpenSSF Scorecard | Оценивать наблюдаемые меры защиты разработки открытого проекта. |
| OWASP Dependency-Track | Отслеживать риски компонентов в портфеле приложений. |

Критерии выведены из вопросов потребителя: какой компонент используется, какие проблемы известны, как принимаются изменения и на чём основан предлагаемый вывод.

| Потребность пользователя | Критерии | Обоснование |
|---|---|---|
| Понять, какой компонент и какую версию собираются использовать. | Состав компонентов; Объект результата | Без состава зависимостей и идентификатора объекта находку нельзя применить к выбранному выпуску. |
| Различить известную уязвимость, вредоносный пакет и проблему собственного кода. | Известные уязвимости; Вредоносные пакеты; SAST исходного кода | Это разные объекты и способы выявления; один отрицательный результат не заменяет остальные проверки. |
| Понять, как контролируются изменения и кто участвует в их подготовке. | Защитные практики; Вклад разработчиков | Проверки ревью и защиты ветвей характеризуют контроль; история вкладов показывает участие, но сама по себе не подтверждает полномочия. |
| Уточнить изменения в публикации выпусков и организационный контекст. | Смена публикующих участников; Участие организаций | Смена публикующего участника и принадлежность к организации требуют разных подтверждений и не доказывают злой умысел. |
| Проверить основание вывода и понять, что делать дальше. | Проверяемое основание; Действия по исправлению | Нужны исходная находка, правило или событие и применимое действие; рекомендация должна быть проверяемой. |

Критерии объединены в три группы: технические сведения, процессы и участие, представление результата. Для каждого критерия задано условие положительной оценки.

Первая группа охватывает состав компонентов, известные уязвимости, вредоносные пакеты и SAST исходного кода проекта. Вторая характеризует контроль изменений, вклад разработчиков, смену публикующих участников и участие организаций. Третья показывает, можно ли отнести результат к объекту анализа, проверить его основание и выбрать действие по исправлению. Такое деление связывает сравнение функций с этапами подготовки решения потребителем.

**Технические сведения**

| Критерий | Условие положительной оценки |
|---|---|
| Состав компонентов | Выявляется или импортируется перечень зависимостей с идентификаторами. В основании различаются собственное выявление и импорт готового SBOM. |
| Известные уязвимости | Выполняется сопоставление проекта или его зависимостей с опубликованными сведениями об уязвимостях. Поиск потенциальных ошибок кода без такого сопоставления сюда не относится. |
| Вредоносные пакеты | Документирован поиск известных вредоносных пакетов либо признаков их подозрительного поведения. В основании различаются эти способы; наличие функции не означает одинакового качества обнаружения. |
| SAST исходного кода | В выбранном модуле выполняется статический анализ исходного кода анализируемого проекта на ошибки безопасности. Анализ только сторонних пакетов не засчитывается. |

**Процессы и участие**

| Критерий | Условие положительной оценки |
|---|---|
| Защитные практики | Инструмент проверяет практики контроля изменений в репозитории, например ревью и защиту ветвей. Запуск собственного сканера в CI не считается исследованием таких практик. |
| Вклад разработчиков | Результат различает авторов изменений и их вклад в репозиторий. Имя владельца пакета без истории изменений недостаточно. |
| Смена публикующих участников | Отслеживается появление нового публикующего участника или изменение владения пакетом. Текущая карточка автора и обычная история коммитов недостаточны. |
| Участие организаций | Рассматриваются аффилиации участников или вклад организаций в проект. Внутреннее подразделение, к которому отнесён проект потребителя, не считается аффилиацией внешнего разработчика. |

**Поддержка решения**

| Критерий | Условие положительной оценки |
|---|---|
| Объект результата | Находка или метрика связана с идентифицированным компонентом, версией, коммитом либо анализируемой ветвью. Конкретный уровень указан в основании; эти объекты не приравниваются друг к другу. |
| Проверяемое основание | Для результата доступны конкретная проблема, связанный код или компонент, сработавшее правило либо исходные события метрики. Один суммарный балл без деталей недостаточен. |
| Действия по исправлению | Предлагаются конкретные сведения об исправлении, рекомендуемая версия или меры улучшения выявленной практики. Простая регистрация нарушения и возможность скрыть его не считаются исправлением. |

Сравнение выполнено по официальным материалам. «Да» обозначает документированную возможность выбранного модуля, «Нет» — прямо указанное ограничение, «Не установлено» — недостаточность сведений. Для каждой оценки сохранены основание, источник и раздел документа.

Область оценки задаётся выбранным модулем и способом его применения. Например, импорт готового SBOM и определение зависимостей по проекту дают сведения о составе разными путями. Для проверок репозитория существенны права доступа, а для предупреждений — ветвь, коммит или версия, к которым они относятся. Эти условия зафиксированы в основаниях оценок и учитываются при разборе результатов.

Всего получено 99 оценок: 9 объектов по 11 критериям.

В Dependency-Track состав поступает из SBOM; Scorecard использует OSV при проверке Vulnerabilities. Это разные способы получения и использования сведений о зависимостях. [7](#source-DT1), [8](#source-SC2)

CodeScoring SCA, Snyk Open Source и Sonatype Lifecycle рассматривают сторонние компоненты как объект технического контроля. Получаемые находки позволяют определить затронутую зависимость и перейти к рассмотрению её исправления. Для потребителя значение имеют способ получения состава, охват поддерживаемой экосистемы и привязка предупреждения к фактически используемой версии. [9](#source-CS1), [10](#source-SN1), [11](#source-SN3), [12](#source-SO1)

Возможности OSA и Lifecycle дополнены применением заданных политик. В CodeScoring OSA результат связан с доступом к компоненту, в Lifecycle настроенные действия могут предупреждать о нарушении или останавливать соответствующий этап. Эти средства показывают, что техническую находку уже можно связать с формализованным действием. При использовании таких результатов в нашей системе потребуется сохранить основание срабатывания и условия правила. [13](#source-CS4), [14](#source-SO2)

Работа с вредоносными пакетами включает сведения об известных пакетах в CodeScoring, Snyk и Dependabot, анализ подозрительных свойств в Socket, политику Security-Malicious в Lifecycle и сопоставление заданных хешей в Dependency-Track. При объединении результатов необходимо сохранять способ получения находки и затронутую версию. [9](#source-CS1), [15](#source-SN4), [16](#source-GH6), [17](#source-SK1), [18](#source-SO4), [19](#source-DT4), [20](#source-DT2)

Способ выявления определяет дальнейшую проверку. Сообщение об известном вредоносном пакете требует установить совпадение компонента и версии. Сигнал о подозрительном установочном скрипте или поведении требует изучить соответствующее действие пакета. В Socket такие признаки представлены предупреждениями о зависимостях и их изменениях. Для рекомендации полезно сохранять тип сигнала вместе с его описанием и источником. [17](#source-SK1), [21](#source-SK2)

По критерию анализа исходного кода самого проекта положительная оценка получена для CodeQL. Socket исследует сторонние пакеты. [22](#source-GH1), [21](#source-SK2)

CodeQL связывает предупреждение с местом в коде и правилом анализа. Dependabot, в свою очередь, связывает сведения об известной проблеме с зависимостью. Совместное рассмотрение этих результатов требует установить, какой участок или компонент затронут и присутствует ли он в выбранной версии проекта. Отсюда следует требование сохранять объект каждой находки при подготовке рекомендации. [23](#source-GH8), [24](#source-GH5)

Защитные практики раскрывает OpenSSF Scorecard: Code-Review и Branch-Protection характеризуют контроль изменений, Contributors использует сведения об авторах и организациях. При получении результатов существенны права доступа и выбранный режим запуска. В частности, состав публичного API отличается от полного набора проверок инструмента. Для интерпретации нужно сохранять, какая проверка выполнялась и какие сведения были доступны. [25](#source-SC1), [8](#source-SC2)

CodeScoring TQI предоставляет историю изменений, сведения об авторах, периодах активности и распределении вкладов. Такой результат полезен для изучения того, как работа распределяется между участниками и как меняется состав сообщества. При подготовке рекомендации важны период наблюдения и роли, к которым относится показатель: авторство изменения, его рассмотрение и публикация выпуска характеризуют разные действия. [26](#source-CS2), [27](#source-CS3), [28](#source-CS5)

Socket выделяет смену публикующих участников как отдельный сигнал. Для потребителя это повод уточнить происхождение выпуска и обстоятельства передачи полномочий. Смысл события определяется его связью с выбранной версией и другими доступными сведениями о публикации. Таким образом, история разработки и события распространения компонента дополняют друг друга. [17](#source-SK1)

Эти сведения отвечают на разные вопросы: кто участвует в работе, как проверяются изменения и кто публикует выпуск. Для рекомендации требуется связать наблюдаемое событие с выбранной версией и определить необходимую проверку.

Поэтому активность проекта целесообразно рассматривать в контексте сопровождения. Например, редкие изменения стабильной библиотеки и прекращение исправления известных проблем требуют разной интерпретации. Пользователю нужны наблюдаемый период, описание обстоятельства и объяснение предлагаемого действия. Такая постановка переводит историю активности в сведения, полезные для выбора компонента.

## Исследовательские подходы

Для обоснования признаков и правил интерпретации рассмотрены четыре исследования зависимостей, вредоносных пакетов и показателей практик разработки.

|---|---|---|---|
| Zimmermann и соавт., 2019. Граф зависимостей, пакетов и сопровождающих; оценка потенциального охвата компрометации. | История npm до апреля 2018 года; 5 386 239 выпусков. Зависимости создают косвенное доверие к сопровождающим; небольшой набор учётных записей имеет большой потенциальный охват. | Структурный потенциал атаки не равен её вероятности. Срез npm не представляет все экосистемы. | Учитывать транзитивные зависимости и различать автора изменения и участника с правом публикации. «Состав компонентов», «Вклад разработчиков», «Смена публикующих участников». Разделы 3.1, 4.2.2–4.2.3 [4](#source-RS1) |
| Ohm и соавт., 2020. Ручной анализ известных вредоносных пакетов и построение деревьев атак. | 174 пакета npm, PyPI и RubyGems; ноябрь 2015 — ноябрь 2019 года. Структурированы пути внедрения и условия исполнения вредоносного кода. | Выборка известных случаев не измеряет распространённость атак и полноту обнаружения. | Разделять известную уязвимость и намеренно вредоносный компонент; проверять сведения о выпуске. «Известные уязвимости», «Вредоносные пакеты», «Объект результата». Аннотация; описание набора и деревьев атак [5](#source-RS2) |

Интерпретация результата зависит от поддерживаемых механизмов; нестандартный способ обновления зависимостей может не учитываться проверкой. | Результаты относятся к изученной версии Scorecard и выбранным экосистемам; это не аудит всех процессов. | Сохранять исходное объяснение проверки и причины отсутствия сведений. «Защитные практики», «Проверяемое основание»; учёт неполноты данных. IV-C; V-10 Dependency-Update-Tool; VII [31](#source-RS3) |

В исследованных моделях R² составлял 0,09–0,12; агрегированный показатель не обеспечивал надёжного прогноза числа уязвимостей. | Опубликованные уязвимости зависят и от обнаружения/раскрытия; связь не доказывает причинность. | Не трактовать общий балл как вероятность безопасности; отдельно показывать прямые находки и неопределённость. Аннотация; таблица III; разделы VI–VIII [32](#source-RS4) |

Исследования определяют способы использования сведений: учитывать транзитивные зависимости и события публикации, сохранять объяснения автоматических проверок, рассматривать показатели практик вместе с конкретными техническими находками.

Работа Zimmermann и соавторов связывает выбор зависимости с доверием к участникам цепочки её сопровождения. Исследование Ohm и соавторов дополняет эту картину описанием способов внедрения и исполнения вредоносного кода. В совокупности они обосновывают внимание к составу зависимостей, полномочиям публикующих участников и происхождению выбранного выпуска. [4](#source-RS1), [5](#source-RS2)

Исследования Zahan и соавторов относятся к интерпретации процессных показателей. Разбор Scorecard показывает значение поддерживаемого механизма проверки: нестандартный способ обновления зависимостей может потребовать отдельного объяснения результата. Работа о связи практик с числом уязвимостей обосновывает совместное рассмотрение показателей и конкретных находок. Для нашей системы из этого следует необходимость сохранять исходное объяснение проверки и явно описывать переход от факта к рекомендуемому действию. [31](#source-RS3), [32](#source-RS4)

Организационный контекст дополняет эти сведения. CHAOSS предлагает анализировать участие организаций и назначение финансовой поддержки. Для нашей задачи существенны источник, период и характер такого участия, а также его связь с сопровождением проекта. [33](#source-N4), [34](#source-N5)

Например, участие организации в изменениях, её роль в рассмотрении кода и поддержка сопровождения дают разные сведения о проекте. Их полезно связывать с наблюдаемыми действиями и опубликованными условиями поддержки. Такой контекст помогает объяснять устойчивость сопровождения и определять, какие обстоятельства требуют уточнения при выборе компонента.

Сравнение показывает, какие результаты уже доступны и какую работу потребитель выполняет при подготовке решения об использовании компонента.

Из таблицы следует, что существующие средства предоставляют значительную часть исходных результатов: состав, находки, оценки практик и историю участия. При подготовке решения потребитель сопоставляет их между собой, проверяет применимость к выбранной версии и определяет дальнейшее действие. На поддержке этого этапа целесообразно сосредоточить разрабатываемую систему.

Разрабатываемая система должна собирать доступные сведения о проекте и связывать их с рекомендацией по явным правилам. Основу анализа составят активность изменений, участие разработчиков и наблюдаемые практики разработки. Результаты готовых проверок кода и зависимостей могут дополнять эти сведения. Из анализа следуют шесть требований.

Привязка результатов разных средств к версии и моменту проверки обосновывает требование указания объекта анализа. Процессные критерии определяют состав собираемых сведений. Наличие у аналогов оснований и действий по исправлению задаёт ориентир для объяснения рекомендации. Статус «Не установлено» показывает необходимость сохранять пробелы в данных и учитывать их при формировании вывода.

| № | Требование | Содержание |
|---|---|---|
| 1 | Указание объекта анализа | Сохранять ссылку на репозиторий, выбранную версию или коммит и дату получения сведений. |
| 2 | Сбор доступных сведений | Получать показатели активности и участия разработчиков; учитывать доступные сведения о защитных практиках и результаты готовых проверок. |
| 3 | Формирование рекомендации | По явно заданным правилам формировать рекомендацию об использовании проекта или необходимости дополнительной проверки. |
| 4 | Объяснение результата | Показывать, какие наблюдаемые факты повлияли на рекомендацию, и приводить ссылки на их источники. |
| 5 | Учёт недоступных данных | Указывать, каких сведений не хватает; не считать невозможность проверки положительным результатом. |
| 6 | Понятное представление | Представлять краткий итог анализа и давать возможность просмотреть показатели, основания и предлагаемые действия. |

Для удобства работы предусматривается графический пользовательский интерфейс.

Практический результат для пользователя — краткая рекомендация и возможность просмотреть повлиявшие на неё факты. Правило связывает наблюдение, условия его применимости и необходимое действие. Например, указание на проблему выбранной версии сопровождается её идентификатором и предлагаемой мерой; изменение активности — периодом наблюдения и пояснением значения для сопровождения. Это делает вывод доступным для проверки по исходным сведениям.

Проверка системы предполагает сопоставление полученных показателей с источниками, а рекомендаций — с заданными правилами на нескольких открытых проектах. Для каждого примера сохраняются исходные сведения, ожидаемый вывод и фактический результат. Отдельно проверяется обработка недоступных данных и известной проблемы выбранной версии.
