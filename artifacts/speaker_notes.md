# Текст выступления

Разработка системы анализа качества процессов разработки проектов с открытым исходным кодом

15 слайдов. Ориентировочная продолжительность доклада 9–11 минут при спокойном темпе.

## Слайд 1. Тема работы

Представляю результаты исследовательского этапа работы по разработке системы анализа качества процессов разработки открытых проектов. Предполагаемый пользователь системы — разработчик или специалист по информационной безопасности, который выбирает внешний компонент. Его задача состоит в том, чтобы понять условия использования проекта и необходимые проверки. В докладе покажу, какие сведения уже предоставляют существующие средства, какую работу пользователь выполняет самостоятельно и какие требования из этого следуют для разрабатываемой системы.

## Слайд 2. Проблема выбора открытого компонента

При выборе открытого компонента сведения о его безопасности приходится собирать из разных источников. Проверка зависимостей сообщает об известных проблемах, репозиторий содержит историю изменений, а настройки показывают порядок принятия кода. Затем нужно установить, относятся ли эти сведения к используемой версии и что они означают для нашего приложения. Масштаб зависимостей увеличивает эту работу. Например, в исследовании истории npm до апреля 2018 года средний пакет транзитивно зависел от кода примерно сорока сопровождающих. Другая работа рассматривает 174 известных вредоносных пакета за период с ноября 2015 по ноябрь 2019 года. Эти исторические результаты показывают значение связей между компонентами, участниками и выпусками. Практическая проблема заключается в подготовке обоснованного решения из разрозненных сведений.

## Слайд 3. Цель и задачи работы

Цель работы — разработать систему анализа процессов разработки открытых проектов для формирования обоснованных рекомендаций об их использовании с учётом информационной безопасности и риска внедрения бэкдоров. Объект исследования — процессы разработки и сопровождения таких проектов. Для достижения цели выделены пять задач. Сначала необходимо проанализировать проблему выбора компонента, сравнить существующие средства и обосновать требования. Затем предстоит определить источники, показатели и правила формирования рекомендаций, спроектировать и реализовать систему с пользовательским интерфейсом. Завершающая задача — проверить показатели по источникам, а рекомендации по заданным правилам на выбранных открытых проектах. Текущий доклад посвящён результатам первых двух задач.

## Слайд 4. Состав и методика сравнения

В обзор включены девять модулей и средств: коммерческие платформы, средства GitHub и открытые инструменты. Модули разного назначения рассмотрены отдельно. Например, возможности CodeScoring TQI не перенесены на SCA, а Dependabot и CodeQL оценены как самостоятельные объекты. Одиннадцать критериев дают девяносто девять оценок. Сравнение выполнено по официальным материалам, для каждой оценки сохранены основание, источник и конкретный раздел документа. Положительная оценка означает документированную возможность. Отрицательная используется при прямо указанном ограничении. Если подтверждения недостаточно, сохраняется статус «Не установлено». Таким образом, сравнение характеризует документированные функции выбранных модулей. Полные основания находятся в аналитическом отчёте и таблице сравнения.

## Слайд 5. Критерии связаны с вопросами пользователя

Критерии выведены из вопросов потребителя и объединены в три группы. Техническая группа помогает установить состав компонентов, известные уязвимости, сведения о вредоносных пакетах и результаты статического анализа кода. Вторая группа описывает процессы и участие: защитные практики, вклад разработчиков, смену публикующих участников и участие организаций. Третья показывает, насколько результат пригоден для подготовки решения. Можно ли связать находку с объектом анализа, проверить её основание и определить действие по исправлению? Эти группы позволяют сопоставить разные средства по их роли в общей задаче выбора компонента. Условие положительной оценки каждого критерия подробно задано в отчёте.

## Слайд 6. Технические сведения о компонентах и коде

Первая матрица показывает технические возможности. Работа с составом компонентов подтверждена у шести средств из девяти, с известными уязвимостями — у семи, с вредоносными пакетами — у шести. При этом способы получения результата различаются. Dependency-Track принимает состав из готового SBOM, а другие средства могут определять зависимости по материалам проекта. Поиск известных вредоносных пакетов и анализ подозрительных свойств также дают разные виды находок. В выбранных границах статический анализ собственного кода проекта подтверждён у CodeQL. Эти различия важны при объединении результатов: вместе с находкой необходимо сохранять объект проверки и способ её получения. Полные основания всех ячеек приведены в отчёте.

## Слайд 7. Процессы разработки и участие

Во второй группе возможности распределены между несколькими инструментами. OpenSSF Scorecard предоставляет проверки ревью и защиты ветвей, а также использует сведения об участниках и организациях. CodeScoring TQI показывает историю изменений и распределение вкладов между разработчиками. Socket выделяет смену публикующих участников как отдельный сигнал. Эти результаты отвечают на разные вопросы. Автор изменения, участник ревью и человек с правом публикации выполняют разные действия. Для подготовки рекомендации требуется учитывать роль участника, период наблюдения и связь события с выбранным выпуском. По этой группе особенно заметна необходимость сохранять причины неполноты сведений: доступность данных зависит и от прав, и от способа запуска проверки.

## Слайд 8. Основания результата и действия пользователя

По третьей группе у всех девяти средств подтверждены связь результата с определённым объектом и наличие проверяемого основания. Действия по исправлению подтверждены у восьми. Это важный результат сравнения: существующие средства уже дают подробности находок и способы их устранения. В зависимости от средства результат относится к компоненту, версии, коммиту или ветви. При объединении этих данных пользователь проверяет, совпадают ли объекты и сохраняется ли актуальность сведений. Поэтому полезность будущей системы связана с согласованием результатов применительно к выбранному проекту. В итоговой рекомендации нужно сохранить исходные основания и объяснить, почему конкретное действие подходит для рассматриваемой версии.

## Слайд 9. Исследовательские подходы

Обзор включает четыре близких исследования. Zimmermann и соавторы рассматривают граф зависимостей npm и связи с сопровождающими. Для нашей задачи это обосновывает учёт транзитивных зависимостей и различий в ролях участников. Ohm и соавторы анализируют известные вредоносные пакеты и пути внедрения кода. Эта работа помогает разделять типы проблем и сохранять сведения о конкретном выпуске. Исследование Zahan и соавторов о Scorecard показывает значение интерпретации отдельной проверки и поддерживаемых ею механизмов. Другая работа тех же исследователей изучает связь практик безопасности с опубликованными уязвимостями. Для рекомендаций из этого следует необходимость показывать отдельные наблюдаемые факты, их основания и полноту доступных данных.

## Слайд 10. Что требуется для подготовки рекомендации

Сравнение позволяет уточнить задачу дальнейшей разработки. Средства анализа кода и зависимостей дают находки и исправления. Пользователь устанавливает их применимость к своей версии. Проверки репозитория описывают защитные практики, но значение результата зависит от доступности данных и условий проверки. История вкладов помогает понять сопровождение, а события публикации требуют уточнения ролей и происхождения выпуска. Во всех этих случаях потребитель связывает полученные сведения с необходимым действием. Разрабатываемая система должна поддержать именно эту работу: объединить доступные результаты по выбранному объекту, применить явные правила и объяснить рекомендацию. Основания исходных проверок при этом остаются доступными пользователю.

## Слайд 11. Предполагаемый сценарий работы

Предполагаемый сценарий начинается с выбора репозитория и версии либо коммита. Пользователь также указывает назначение компонента, если оно существенно для интерпретации. Затем система получает доступные сведения об активности, участии и защитных практиках. Результаты готовых проверок кода и зависимостей могут дополнить эти данные. На следующем этапе явно заданные правила связывают наблюдаемые факты с рекомендацией и необходимыми проверками. Пользователь получает краткий итог и может открыть показатели, источники и объяснение. Графический интерфейс нужен для удобной работы с этим результатом. На текущем этапе этот сценарий задаёт основу для проектирования и последующей реализации.

## Слайд 12. Требования к разрабатываемой системе

На основе анализа сформулированы шесть требований. Первое — сохранять объект анализа и дату получения сведений. Второе — собирать доступные показатели активности, участия и практик разработки, дополняя их результатами готовых проверок. Третье — формировать рекомендацию по явно заданным правилам. Четвёртое — объяснять результат через повлиявшие факты и ссылки на источники. Пятое — показывать недостающие сведения и учитывать их в выводе. Шестое — представлять краткий итог с возможностью изучить детали и предлагаемые действия. Эти требования описывают конкретный результат программы. Они позволяют последовательно реализовать сбор данных, правила и представление результата, а затем проверить каждый элемент по исходным сведениям.

## Слайд 13. Условный пример применения правила

Покажу простой пример, который иллюстрирует ожидаемую логику. Предположим, что для выбранной версии зависимого компонента опубликована известная уязвимость и указана исправленная версия. Проверка подтверждает, что используемая версия входит в затронутый диапазон. Тогда правило связывает этот факт с рекомендацией обновить компонент до исправленной версии и повторить проверку. В результате пользователь должен увидеть сам компонент, используемую версию, источник сведений, условие срабатывания и предлагаемое действие. Если часть процессных данных недоступна, система отдельно показывает этот пробел и необходимую проверку. Такой пример помогает конкретизировать связь между входными сведениями, правилом и объяснением рекомендации.

## Слайд 14. Проверка системы на открытых проектах

Проверка будет опираться на выбранные открытые проекты и заранее описанные примеры. Сначала показатели системы сопоставляются с исходными сведениями репозитория и результатами готовых проверок. Затем для каждого примера фиксируются применимое правило, ожидаемая рекомендация и фактический результат. Отдельно проверяется поведение при недоступных данных и при известной проблеме выбранной версии. Для этих случаев важно сохранить правильную привязку к объекту и понятное объяснение. Результатом проверки станет перечень совпадений и расхождений с указанием их причин. Такой порядок позволяет оценить, правильно ли система получает сведения и следует ли установленным правилам формирования рекомендаций.

## Слайд 15. Результаты исследовательского этапа

По итогам этапа проанализирована проблема выбора открытых проектов, выполнено сравнение девяти средств по одиннадцати критериям и рассмотрены четыре близких исследования. Результаты оформлены в аналитическом отчёте и таблице сравнения. Анализ показывает, какие сведения уже доступны пользователю и какие действия нужны для подготовки решения по выбранному компоненту. На этой основе обоснован рекомендательный подход и сформулированы шесть требований. Следующий этап — уточнить источники и показатели, разработать правила, реализовать систему и проверить её работу на открытых проектах. Ожидаемый результат для пользователя — рекомендация об использовании проекта с понятными основаниями и необходимыми действиями. Спасибо за внимание.
